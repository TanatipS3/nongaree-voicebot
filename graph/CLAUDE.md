# graph/ — routing, retrieval, memory, emotion

Loaded when working under `graph/`. Moved out of the root `CLAUDE.md` on 2026-09-14 (snapshot: `CLAUDE.md.before-doctor-trim-2026-09-14`). The root file keeps the always-relevant prohibitions.

## Conversation memory (`graph/conversation.py`, `graph/conversation_store.py`)

Memory lives in `graph/`, not `agent.py`, so an offline harness can drive the *same* code — `agent.py` can't be imported without `livekit`. Four things are easy to get wrong:

- **Recording is hung off the detail task, via `make_turn_recorder()`.** Both answer paths used to append only after the last audio frame played, so the turn was absent from `memory` for the whole spoken answer and a follow-up asked mid-answer was routed with an empty history (→ `out_of_scope`). Worse on the typed path: `_cancel_current_speech()` **cancels** `_process_text_and_speak`, so the tail append never ran and the turn was lost outright. The detail answer is what `append_turn` stores anyway (`detail or spoken`), it completes seconds before the audio, and a done-callback survives cancellation. The tail `record_turn(...)` call is a guarded fallback for a turn that produced speech but no panel answer — it is a no-op once the callback has fired.
- **The user's numbers are pinned mechanically, not summarized.** `summarize_history` runs on `ROUTER_MODEL` (an 8B model, 3 sentences) and dropped figures like "80,000" most of the time. `extract_user_facts()` + `pin_facts()` add a `ข้อมูลที่ผู้ใช้ระบุ:` line **after** the LLM writes the summary, so it cannot drop them. Facts are **ranked, not truncated by recency** (keeping the newest 8 let incidental digits evict the turn-1 salary), deduped on **number + unit** (`ข้อ 3` was overwriting `ลูก 3 คน`), and known units are matched before a generic short-word fallback (Thai is unspaced, so a naive match on `100,000 บาทต้องจ่าย` yields `บาทต้อ`).
- **Compaction runs in the background, so it must not assume history stood still.** `maybe_summarize()` awaits a multi-second LLM call; turns can be appended during it. It records **how many** entries it summarised (`cut`) and afterwards keeps `history[cut:]` — never a "recent" list sliced before the await, which silently dropped every turn asked mid-summary (numbers included, and from disk on the next save). If the history list was *replaced* during the wait it discards the summary instead. The background task is held in `_background_tasks` in `agent.py` because the event loop only keeps weak references to tasks. Covered by `test_compaction_race` (`HANDOFF.md` §3e Fix 26).
- **Persistence is per user, keyed on the LiveKit room name** minus the `nongaree-` prefix (`conversation_store.room_to_key`). The token route derives the room server-side, so the key is sanitised and unspoofable — **don't switch it to `participant.identity`**, which is the raw username. Atomic write, 30-minute idle TTL matching `IDLE_LIMIT_MS`, and it degrades to in-process memory with a single warning if `MEMORY_DIR` is unwritable.

`scripts/test_conversation.py` covers all of the above offline — no Qdrant, no LiveKit, no network.

## The graph (`graph/graph.py`)

`START → parallel → {generate | out_of_scope | curated} → END`. Only **one** node runs per turn.

`parallel_node` decides the route, short-circuiting in order:
1. `_manual_emotion_command()` — user asking Aree to *show* an emotion ("ทำหน้าเศร้า") → `curated` route with a canned line. **Matches only a message that IS a command, anchored end to end** — it used to fire on a command word + emotion word anywhere, so "จ้างฟรีแลนซ์ (บุคคลธรรมดา) ทำระบบ…" ("ทำ" + "ธรรมดา") became "กลับสู่อารมณ์ปกติ". The **same check runs in the browser** (`getManualEmotionCommand` in `VoiceRoom.tsx`) *before* a typed question is sent, so a false match there swallows the question entirely — keep the two equivalent (`scripts/test_conversation.py` asserts the alias lists match).
2. `find_curated_answer()` (`graph/curated_answers.py`) — hand-written exact answers for fragile short-codes/forms (e.g. TCL) and simple calculators → `curated`. Two guards added 2026-09-14 after a supervisor scenario test: **`_covers()`** — each topic-specific canned answer declares the topics it covers (`_TOPIC_TERMS`) and is skipped if the question also mentions anything else, so a multi-part question ("ThaiESG + ประกันชีวิต", "ฟรีแลนซ์ + หักค่าใช้จ่าย", "…เปลี่ยนเป็นบริษัท") reaches retrieval instead of getting a partial answer; and **`_is_annual_salary()`** — the salary calculators assume a monthly figure (×12), so a yearly one ("เงินเดือนรวม / ทั้งปี / …บาทต่อปี") skips them. The yearly marker must sit on the salary amount: in "เงินเดือน 100,000 บาทต้องจ่ายภาษีปีละเท่าไหร่" the "ปีละ" belongs to the tax.
3. `_fast_route()` — keyword/regex classifier (`rag` / `direct` / `out_of_scope`). This handles most traffic **without an LLM call**. Tax-form patterns, mixed alphanumeric codes, and English tax terms (see *English term aliases*) force `rag`. **First check of all** is `_is_provider_recommendation()` → `out_of_scope`: "which bank / which company / which fund is best" is not something RD answers at any confidence. It must run before the keyword lists, because `ประกันชีวิตบริษัทไหนดีที่สุด` contains "บริษัท", routes `rag`, and then retrieves at 0.82 — the score gate never gets a chance. Keyed on a **provider noun + "ไหน"**, never "ไหน" alone (`ต้องยื่นแบบไหน` — "which form" — is a good tax question).
   **3b. LLM follow-up classifier** (`classify_followup`, `HANDOFF.md` §3e Fix 27). When `_fast_route` says `out_of_scope`, there is an earlier user question, the keyword follow-up rescue didn't fire, and it isn't a provider-recommendation question, one yes/no LLM call asks "does this depend on the previous turn?". **1** → route `rag` *and* set `state["is_followup"]`, which makes retrieval widen with the previous question even without an anaphora marker. **0, timeout (2.5s) or unparseable** → today's keyword behaviour. It is gated precisely so a normal tax question, a first question, or "which bank is best" never pays for an LLM call. Model is `GENERATE_MODEL` (ptm-oss-120b), **not** `ROUTER_MODEL`: measured, the 8B model was less accurate (11/14 vs 14/14) *and* twice as slow, because it always emits `<think>` first. **Classification, not rewriting** — an LLM rewrite of the same cases turned the weather question into the previous tax question.
4. Only if `_fast_route` is inconclusive (or `ROUTER_USE_LLM=true`) does the **LLM router** (`router_node`) run, in parallel with retrieval; retrieval is cancelled if the router says non-RAG.

Routes `direct` and `rag` both go to `generate_node` — the difference is whether `state["context"]` is populated. When `RAG_ENABLED=false`, retrieval is skipped entirely.

**Three-way separation — read before touching the router.** `_fast_route()` returning `"out_of_scope"` is a **fallthrough, not a decision**: it means none of the 33 `_FAST_RAG_KEYWORDS` / 5 `_FAST_DIRECT_KEYWORDS` matched, so the bucket holds both genuinely off-topic questions *and* real tax questions phrased outside those keywords. Three outcomes must stay distinct:

| Case | Route | Response |
|---|---|---|
| Tax question with data | `rag` | Real answer + citations |
| Tax-shaped, retrieval empty | `curated` | Apology + **full contact table** (1161 + hours, e-Appointment, office finder) |
| Keyword fallthrough | `out_of_scope` | **Conditional** wording ("if this is a tax question, call 1161") + one-line pointer |

Collapsing these breaks in both directions: put the staff handoff on `out_of_scope` and someone asking about the weather is told to call the call centre; leave `out_of_scope` asserting "outside our scope" and a misclassified tax question is dead-ended. The `OUT_OF_SCOPE_USE_LLM=true` branch is deliberately *not* hedged — that path is a genuine determination. The flag defaults to `false`.

**Abstain path:** if a `rag` turn retrieves nothing usable, `_no_source_response()` rewrites the turn to route `curated` with the canned `NO_SOURCE_ANSWER`, short-circuiting *both* generators with **no LLM call**. This is deliberate — with an empty context the generator would answer from model knowledge instead of the KB, which is exactly the hallucination being avoided. **Don't "fix" this by letting `generate_node` run on empty context.** `NO_SOURCE_ANSWER`'s line order is also load-bearing: `compact_spoken_answer()` speaks only the **first two lines**, so the apology + "โทร 1161" are spoken and the contact table stays screen-only. Don't reorder it.

**Follow-up widening.** `build_retrieval_query(query, messages)` prepends the previous question to short anaphoric follow-ups ("แล้วถ้ามีลูก 3 คนล่ะ") — a bare follow-up measured **0 characters retrieved**, every time. It widens **only the retrieval query**; routing, answering and display are untouched. Fires only when the query is ≤ `_FOLLOWUP_MAX_CHARS` (40) **and** hits `_ANAPHORA_MARKERS`; skips form-code/alphanumeric queries so the lexical-first `[EXACT_MATCH]` path stays clean. Two rules from `HANDOFF.md` §3b Fix 4:
- **Don't reuse `_FOLLOWUP_KEYWORDS` here** — it contains "ค่ะ"/"ครับ", which appear in ordinary self-contained questions.
- **Order is `follow-up + previous`, and it matters.** The reverse measured 0 chars on a pair where this order gave 1894 (the combined vector fell under `RAG_SCORE_THRESHOLD`). Don't "tidy" it.

`_is_tax_followup()` has **three** triggers and must keep all of them: `_FOLLOWUP_KEYWORDS` (affirmatives), `_ANAPHORA_MARKERS` (17 — the "แล้วถ้า… ล่ะ" shape), and `_PROCEDURAL_FOLLOWUP_TERMS` (8 — "which documents / which steps / by when / where"). A rescued follow-up routes to **`rag`**, not `direct`, or the widening never runs. These keyword triggers are the fast path; follow-ups phrased outside them fall through to the LLM classifier (step 3b). Both rescues **skip provider-recommendation questions** — before 2026-09-14 "แล้วธนาคารไหนดอกเบี้ยสูงสุดล่ะ" after a tax turn was rescued to `rag` purely on its "ล่ะ". This only shows up end-to-end; tests that call `parallel_node` with the route pre-set bypass the classifier entirely.

> **`_PROCEDURAL_FOLLOWUP_TERMS` is concrete NOUNS, never bare interrogatives, and that is the whole design.** `ยังไง` and `อะไร` appear in `วันนี้อากาศเป็นยังไง` just as readily; keying on those rescues the weather question and collapses the three-way separation. A second safety layer is that `_is_tax_followup()` still requires the RECENT CONTEXT to contain a tax keyword, so these terms can only fire inside a conversation already about tax.

**Retrieval candidate cascade.** `build_retrieval_candidates(query, messages)` returns an ordered list of **`(query, allow_low_score_rescue)` pairs** and `retrieve_node` takes the first that returns anything (`RETRIEVAL_CASCADE=false` restores one-query-one-attempt). No single anchor rule wins — each candidate rescues turns the others return 0 on:

1. today's widened query (previous user question, if anaphoric and short)
2. the bare query
3. the query with English tax terms rendered in Thai
4. `query + conversation opener` — **rescue flag OFF**
5. `query + previous answer[:240]`, **only if the query is anaphoric** — **rescue flag OFF**

The cascade only advances after a candidate has already come back empty, i.e. on turns already headed for the "call 1161" handoff, so it cannot over-widen a working turn.

**The `allow_low_score_rescue` flag is load-bearing, and it gates BOTH ways around the score gate** — the low-score rescue *and* the exact-code shortcut. Candidates 4 and 5 are built from *borrowed* context, and neither bypass may argue from words the user didn't use. A query containing its own form code gets exactly one candidate (flag true), so a code reaching the retriever with the flag false is always borrowed: without that check, a conversation that *opened* on `ภ.ง.ด.90 คืออะไร` answered a later unrelated question with the ภ.ง.ด.90 chunk (fixture `formcode_opener_guard`). For the rescue specifically: Without the flag an off-topic question inherits tax vocabulary from the opener and then uses the inherited words to argue past the gate — measured: `ค่าจ้างขั้นต่ำปีนี้เท่าไหร่`, `จดทะเบียนสมรสใช้เอกสารอะไร` and `แล้วถ้าอยากซื้อคอนโดล่ะ` all leaked exactly that way. The anaphora gate on candidate 5 is separately load-bearing: it is the only candidate that rescues the salary-calculator chain, and also the only one that can inject a *different topic's* vocabulary.

`AgentState` (`graph/state.py`) carries `sources: list` alongside `context` — citation records for the chunks behind the answer. **Only the `rag` branches actually set it**; the manual-emotion, curated, `direct` and `out_of_scope` branches omit the key entirely, so read it as `state.get("sources") or []` (which is what `agent.py:send_sources` does).

## Retrieval (`graph/retriever.py`)

**The score gate is not just `RAG_SCORE_THRESHOLD`.** That threshold (0.75) compares the top **dense** score only, and it is simultaneously too strict and too loose: genuine tax follow-ups measure 0.72–0.73 while off-topic questions reach 0.82. **Do not try to fix this by moving the threshold** — the two populations interleave and no value separates them. `scripts/threshold_sweep.py` proves it and prints the verdict; run it before reopening the question. Instead, `_should_rescue_low_score()` reconsiders a rejected query on two signals the gate never saw:

- **Lexical ≥ `_LEXICAL_RESCUE_MIN` (12.0).** Not a fitted number — `_lexical_scored` awards exactly +12.0 when the whole normalized query appears verbatim in a chunk, so this is the line between "the corpus contains this phrasing" and "some words overlapped". Lexical is a high-precision **positive** signal only; it can rescue, never reject (many on-topic questions score ~1.0). **A lower cut leaks:** `จดทะเบียนสมรสใช้เอกสารอะไร` reaches 6.8 purely from the +6.0 `_DOCUMENT_TERMS` bonus on "เอกสาร".
- **Explicit tax vocabulary above a `_TAX_VOCAB_RESCUE_FLOOR` of 0.72.** The floor exists because `ภาษีคาร์บอนเครดิตฟาร์มกุ้งคำนวณยังไง` is *also* explicitly about tax and **must keep abstaining** — it measures 0.6984, a 0.02 margin. **Don't tighten it**, and don't delete the `unanswerable_guard` fixture that holds it down.

Note the lexical scan runs only for queries already headed for the handoff, so it costs nothing on the happy path.

**English term aliases.** The corpus is Thai and bge-m3 does not map English abbreviations onto it — an English token actively drags the whole query vector down. Measured: `VAT คิดกี่เปอร์เซ็นต์` 0.6811 → 0 chars; **adding** Thai alongside (`ภาษีมูลค่าเพิ่ม VAT …`) 0.7193 → still 0; **replacing** it (`ภาษีมูลค่าเพิ่มคิดกี่เปอร์เซ็นต์`) 0.7721 → 2983 chars. So `_ENGLISH_TERM_ALIASES` / `_alias_expanded_query()` (in `graph/nodes.py`) **replace**, and feed both a cascade candidate and the `_fast_route` decision. Routing off the alias table rather than adding `cit`/`pit`/`wht` to `_FAST_RAG_KEYWORDS` is deliberate — that list is matched as a **bare substring**, so "cit" would fire inside "citizen" and "facility".

**Payload trap:** `review_flags`, `ref_links` and `image_urls` are stored in Qdrant as **JSON-encoded strings**, not arrays — `if md.get("ref_links")` is true for the string `"[]"`. Parse with `_json_list()`, or every count comes back as the full point count.

Corpus facts that shaped the citation design (measured over 1311 points): only **23 chunks (1.8%)** have real `rd.go.th` URLs, so a link-based citation UI would look broken 98% of the time — a URL is shown only when one exists. **969 (74%)** are flagged `needs_tax_review` and **143 (11%)** `possibly_outdated`. Only `possibly_outdated` surfaces a warning in the hover card today; `needs_tax_review` is carried in the data but not shown. `HANDOFF.md` §3b Fix 6 flags this as an open question the user hasn't ruled on — citation raises perceived authority over a corpus that is mostly self-flagged as unreviewed.

## Emotion post-processing

`normalize_emotion()` (`graph/nodes.py`) and `normalize_stream_emotion()` (`agent.py`) override the LLM's tag from keyword context: any "sad" trigger wins; `angry` is downgraded to `idle` unless a severe-case term is present; `idle` is promoted to `happy`/`wow` on positive terms. Valid set: `happy, sad, angry, wow, sleep, idle`. The keyword tables (`_ANGRY_CONTEXT_TERMS`, `_SAD_CONTEXT_TERMS`, `_HAPPY_CONTEXT_TERMS`, `_WOW_CONTEXT_TERMS`) are **duplicated in both files** — change both.

> **They drifted once — `_ANGRY_CONTEXT_TERMS` was 13 in `agent.py` and 15 in `graph/nodes.py`.** Fixed 2026-09-10 by trimming nodes.py to match; all four tables are now identical and `scripts/test_conversation.py` **asserts that**, so a one-sided edit fails a test instead of silently diverging.
>
> `_ANGRY_CONTEXT_TERMS` is an **allow-list** — it lets an LLM-proposed `angry` stand and downgrades everything else to `idle`; it never forces angry. The two removed terms were substring false-positive generators: `ปรับ` fires inside `ปรับปรุง` ("ขอปรับปรุงข้อมูลผู้เสียภาษี" → angry) and `เงินเพิ่ม` inside `เงินเพิ่มเติม` ("ต้องจ่ายเงินเพิ่มเติมไหม" → angry), both benign. `เบี้ยปรับ` is the precise term and was already present. `AREE_SYSTEM_PROMPT` scopes angry to หนีภาษี / ทุจริต / เอกสารปลอม / คดีอาญา and explicitly excludes ordinary tax explanations.
>
> Beware: all four tuples end with the same lines, so a naive `str.replace` edit hits more than one of them.
